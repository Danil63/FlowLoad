# FlowLoad: инженерный аудит

## Область проверки

Статический анализ каталога Swagger, удаления методов и документов, запуска k6, локальных файлов, браузерных черновиков и изоляции окружений. Регрессионные тесты используют временные каталоги и имитацию Makefile, без запросов нагрузки к игре. В Chrome на изолированных данных проверены отображение повреждённых файлов рядом с исправными, открытие исправного сценария и восстановление черновика после перезагрузки. Полноценное профилирование больших каталогов и ручная проверка нескольких браузерных вкладок не выполнялись.

## Исправлено

| Проблема | Изменение |
| --- | --- |
| Валидация учитывала только журнал удалений, но не неизвестные ID | Общая проверка для браузера и сервера: метод с ID должен существовать, принадлежать документу и совпадать по HTTP-методу и пути |
| Каталог перечитывался для каждого сценария/профиля | Один снимок каталога и индекс Map/Set на каждый запрос списка; проверки ссылок линейны по числу шагов вместо перебора всех удалений для каждого шага |
| Удаление или перезапись могли конкурировать с проверкой и запуском | Изменения и запуск сериализованы внутри одного процесса; редактирование данных во время теста возвращает 409 |
| Частичная запись JSON при параллельном чтении | Сценарии и профили сохраняются через уникальный временный файл и атомарное переименование |
| Нет явной политики HTTP-кеширования | JSON API и статические файлы получают Cache-Control: no-store; браузерные запросы также отключают кеш |
| Фоновая вкладка могла показывать старый каталог | При возврате фокуса/видимости обновляются каталог и списки; удалённые методы в профиле отмечаются как невалидные |
| Два сервера могли менять одну папку данных | `proper-lockfile` блокирует канонический путь проекта независимо от порта; второй процесс завершается с понятным сообщением |
| Один повреждённый файл скрывал весь список | Сценарии и профили читаются по отдельности; проблемный файл остаётся красной строкой с диагностикой, открытие и запуск отключены |
| Запуск JSON без корректных шагов/целей | Сервер повторно проверяет структуру перед запуском; повреждённый или недоступный файл возвращает 409 без запуска генератора |
| Частая синхронная запись больших черновиков | Сохранение отложено на 250 мс, одинаковое содержимое не записывается повторно, каталог после миграции не дублируется в черновик; при уходе со страницы выполняется принудительное сохранение |
| Переполнение localStorage прерывало обработчик | Ошибка показывается отдельно; последний сохранённый черновик сохраняется, ожидающая запись повторяется при следующем сохранении |
| Неограниченный рост истории запусков в памяти | Максимум 30 записей, срок завершённых запусков 1 час, очистка раз в минуту и при новом запуске; активный тест не удаляется |
| Метод без необязательного `tags` ломал отрисовку | Поиск и карточки используют пустой массив тегов, если поле отсутствует |
| Последнее сохранение могло уничтожить изменения другой вкладки | GET и списки возвращают SHA-256-ревизию содержимого. Сохранение и удаление проверяют исходную ревизию внутри очереди изменений; устаревшие запросы получают 409 |
| Устаревший редактор мог восстановить удалённый файл | Запрос с ревизией исчезнувшего файла отклоняется; пользователь явно сохраняет новую копию |
| Общий черновик затирался другой вкладкой | Рабочий черновик и исходная ревизия хранятся в sessionStorage каждой вкладки; localStorage используется как последняя резервная копия для нового открытия |
| Повреждённый каталог или реестр могли останавливать работу без восстановления | Проверка схемы, контрольной суммы и принадлежности копии окружению; явное восстановление последней подготовленной записи, с архивированием оригинала |
| Отсутствующий основной файл мог выглядеть как новое пустое хранилище | При существующей записи восстановления чтение возвращает 503; повторная миграция или импорт не заменяют потерянный каталог |
| Реестр окружений мог скрывать даже страницу диагностики | Статика и lifecycle не зависят от чтения реестра; UI показывает недоступность, создание окружения отключено |

Ревизия вычисляется по содержимому файла, поэтому работает для старых файлов и после перезапуска без изменения JSON-формата сценария. При конфликте интерфейс не подменяет исходную ревизию актуальной автоматически: показывает модальное окно и предлагает продолжить редактирование или сохранить копию. Создание файла с занятым именем также возвращает конфликт. Для старого черновика без известной ревизии существующий файл нельзя перезаписать: нужно открыть его заново или выбрать другое имя.

HTTP-контракт сохранения/удаления расширен полем `baseRevision`. Для нового имени допускается null или отсутствие поля; для существующего файла нужна ревизия из GET или списка. Новый UI передаёт её автоматически. Старые вкладки после обновления нужно перезагрузить. Проверка защищает изменения через сервер FlowLoad; сторонний процесс, напрямую записывающий файлы между проверкой и записью, не участвует в этой блокировке.

При обычном завершении сервера блокировка снимается автоматически. SIGINT/SIGTERM ожидают очередь сохранений и активный тест; новые изменения получают 503. После аварийного завершения блокировка считается устаревшей через 30 секунд без обновления. Это файловая heartbeat-блокировка, не защита от ручного редактирования файлов или от старой версии сервера без блокировки. После обновления нужно остановить прежние процессы и запустить новую версию. После SIGKILL отдельно убедитесь, что дочерний k6 не остался работать.

Очистка истории касается только оперативной памяти. HTML-отчёты на диске не удаляются. Проверки токенов после истечения истории нельзя восстановить из памяти сервера: потребуется новый запуск проверки.

Черновик с удалённым шагом намеренно сохраняется: пользователь видит повреждённую связь и может её исправить. Это не восстановление удалённого метода в каталоге. Перед запуском сервер повторно проверяет сохранённый сценарий. Для старых сценариев без ID сохраняется консервативная проверка по журналу удалённых пар «метод + путь».

## Оставшиеся риски

1. **Синхронизация вкладок и объединение правок.** Устаревшие сохранения и удаления уже отклоняются, но списки в фоновой вкладке обновляются при возврате, а не мгновенно через события. Автоматического объединения изменений нет. Для нового открытия хранится только последняя общая резервная копия черновика; независимые рабочие копии живут в сессиях открытых вкладок. При запрете sessionStorage полной изоляции черновиков нет, UI показывает предупреждение о сохранении.
2. **Большие каталоги и списки.** Тысячи карточек требуют виртуализации и замеров времени отрисовки. Каталог больше не копируется в черновик, но сериализация самого большого сценария остаётся синхронной. Списки файлов перечитываются при обновлении страницы; нужны измерения до введения кеша.
3. **Журнал удалений и отчёты растут на диске.** Нельзя просто очищать журнал: от него зависят старые сценарии без ID. Нужны миграция всех ссылок и явная политика хранения/очистки.
4. **Большая проверка токенов.** Число запусков ограничено, но результаты каждого токена хранятся в массиве запуска. Для больших файлов нужны порционная выдача и отдельный лимит объёма результата.
5. **Пределы локального восстановления.** Реестр и каталоги теперь защищены проверяемой копией каждой новой записи; старые файлы нужно защитить командой `make storage-backup` либо следующим изменением. Нет внешнего бэкапа, истории всех версий и гарантии при потере обоих файлов или сбое диска/питания. При повреждении самой копии восстановление останавливается, даже если основной файл выглядит исправным: выбор источника требует ручного разбора. Чтение двух файлов и проверка SHA-256 добавляют работу; это следует измерить на больших каталогах перед оптимизацией, не заменяя проверку устаревающим кешем.
6. **Точность бизнес-сценария.** Автоматическая корреляция ID, тел запросов и способов авторизации отсутствует. HTTP 200/проверка тела не заменяют бизнес-проверки. Пропущенные изменяющие методы нельзя считать протестированными.

## Следующий этап

Следующий приоритет: синхронизация вкладок событиями и профилирование больших Swagger-документов перед виртуализацией карточек. Отдельно ограничить размер результата проверки большого файла токенов. Не добавлять общий долгоживущий кеш каталога без ревизий: он усложнит корректную инвалидацию.

Восстановление реализовано через `make storage-check`, `make storage-backup` и `make storage-recover STORE=... WORKSPACE=... CONFIRM=1`. Требуется остановить сервер. Сначала сохраняется новая запись восстановления, затем основной файл; несовпадение блокирует чтение до явного восстановления, а не откатывает удаление. Чтения и изменения одной пары сериализованы. Перед восстановлением исходник архивируется без изменения байтов. Формат основных JSON сохранён; служебная копия содержит версию, область данных и контрольную сумму. Это обнаружение случайного повреждения, а не криптографическая аутентификация от злоумышленника с доступом к диску.

## Регрессия

`node --test ui/*.test.mjs`: 54 успешных проверки на момент этого изменения. Включены удаление одного метода/документа, повторный импорт, перезапуск, изоляция окружений, неизвестные/изменённые ссылки, атомарная запись, запрет редактирования во время запуска, HTTP-заголовки кеша, повреждённые файлы, межпроцессная блокировка, завершение сервера во время теста, лимит/TTL истории, ошибки браузерного хранилища и разделение черновиков вкладок.

Для восстановления проверены неверный JSON и неверная структура, отсутствие основного файла, повреждённая/чужая копия, несовпадение версий, сбой записи основного файла и копии, конкурентные чтения, сохранение повреждённых байтов и отказ без подтверждения. Сквозные HTTP-тесты подтверждают 503 без запуска генератора, работу исправного окружения, сохранение ID/токенов и блокировки удалённых методов после восстановления. Make-команды проверяются в отдельном временном проекте. В Chrome проверено отображение диагностики повреждённого реестра без пустой страницы.

Сквозная проверка для сценариев и профилей отправляет два конкурентных сохранения с одной ревизией: только одно проходит. Проверены отказ устаревшего удаления, коллизия имени, попытка восстановления удалённого файла устаревшим редактором, создание копии и сохранение актуальной ревизии после перезапуска. В Chrome проверены окно конфликта на обычной ширине и на 390 px, сохранение копии без изменения оригинала и повторное сохранение копии после перезагрузки.

В тесте сохранения 100 быстрых изменений объединяются в одну сериализацию и запись; одинаковый следующий снимок не записывается. Это проверка алгоритма, не измерение FPS или быстродействия на реальном большом Swagger.
