# FlowLoad: план нагрузочного тестирования игрового API

## Цель

Проверить, выдерживает ли production API и игровой backend ожидаемую активность игроков без деградации пользовательского опыта: открытие игры, загрузку профиля, просмотр маршрутов, запуск и завершение полета, карусель, магазин и розыгрыши.

Стратегия гибридная:

- основная нагрузка создается через k6 API-тесты;
- браузерные мобильные smoke-тесты используются точечно, чтобы подтвердить, что игра открывается, canvas живой и маршрут стартует;
- state-changing сценарии запускаются только осторожно, потому что меняют прогресс, экономику и лимиты аккаунта.

## Контур

- Среда: production.
- API: `https://entreporgneur-big-journey-7b03.twc1.net`
- Swagger: `https://entreporgneur-big-journey-7b03.twc1.net/docs`
- Авторизация: cookie `__Secure-better-auth.session_token`.
- Инструмент нагрузки: k6.
- Локальный запуск: один или несколько MacBook.

## Бизнес-процессы и маршруты

| Бизнес-процесс | Что имитируем | API маршруты | Тип теста | Команды | Позитивный результат |
| --- | --- | --- | --- | --- | --- |
| Открытие игры | Игрок открывает мобильную игру после авторизации | `GET /profile`, `GET /aircraft`, `GET /quests`, `GET /collections/me`, `GET /raffles/me`, `GET /wheel/rewards`, `GET /carousel` | Auth read-only | `make auth-1`, `make auth-5`, `make auth-50`, `make auth-100` | Ошибок меньше 1%, checks выше 99%, p95 меньше 1000 ms, p99 меньше 2000 ms, нет 401/403/429/5xx |
| Публичная витрина | Клиент получает публичные справочники | `GET /health`, `GET /routes`, `GET /routes/map`, `GET /shop`, `GET /raffles`, `GET /cities/{cityId}` | Public read-only | `make public-10`, `make public-50`, `make public-100`, `make public-300` | Ошибок меньше 1%, checks выше 99%, p95 меньше 800 ms, p99 меньше 1500 ms |
| Критический полет | Игрок запускает и завершает полет | `GET /profile`, `POST /flights/start`, `POST /flights/{flightId}/complete`, `GET /profile` | State-changing | `make flight-once` | Есть `flightId`, завершение возвращает награду, профиль консистентен, нет дублей и отрицательных балансов |
| Карусель | Игрок смотрит и запускает карусель наград | `GET /carousel`, позже `POST /carousel/run`, затем `GET /profile` | Read-only, затем limited write | Пока read-only внутри `make auth-*` | Корректное состояние карусели, одна награда на один запуск, нет двойных списаний |
| Магазин | Игрок открывает магазин и покупает предметы | `GET /shop`, позже `POST /shop/{itemId}/purchase`, `POST /shop/repeat-flight/redeem` | Public read-only, затем limited write | `make public-*`, позже отдельный shop сценарий | Каталог стабилен, покупка атомарна, баланс не уходит в минус |
| Розыгрыши | Игрок смотрит розыгрыши и участвует билетами | `GET /raffles`, `GET /raffles/me`, позже `POST /raffles/{raffleId}/enter` | Read-only, затем limited write | `make public-*`, `make auth-*`, позже raffle сценарий | Билеты списываются один раз, entry создается корректно, нет дублей |
| Задания и коллекции | Игрок получает прогресс и забирает награды | `GET /quests`, `GET /collections/me`, позже `POST /quests/{questId}/claim` | Read-only, затем limited write | `make auth-*`, позже quest claim сценарий | Прогресс не теряется, награда не выдается повторно |
| Browser smoke | Реальная мобильная страница игры открывается в браузере | Frontend URL, cookie injection, canvas, старт маршрута | Browser smoke | `make browser` | Игра открылась, canvas появился, старт полета работает, критических JS/runtime ошибок нет |

## Этапы запуска

### Этап 0. Диагностика

Команды:

```bash
make ping
make auth-status
```

Позитивный результат:

- `/health` отвечает HTTP 200;
- auth endpoints отвечают HTTP 200;
- нет DNS ошибок, `status=0`, 401, 403.

### Этап 1. Smoke

Команды:

```bash
make public-10
make auth-1
```

Позитивный результат:

- 0% HTTP ошибок;
- все checks успешны;
- p95 не превышает целевые значения.

### Этап 2. Базовая нагрузка

Команды:

```bash
make public-50
make auth-5
```

Позитивный результат:

- error rate меньше 1%;
- p95 public меньше 800 ms;
- p95 auth меньше 1000 ms;
- нет деградации в течение hold-периода.

### Этап 3. Рост нагрузки

Команды:

```bash
make public-100
make auth-50
make auth-100
```

Позитивный результат:

- система держит рост без 429/5xx;
- p99 остается в разумном диапазоне;
- нет резкого роста latency по одному endpoint;
- результат не ограничен CPU/RAM/Wi-Fi локальной машины.

### Этап 4. Распределенная нагрузка с ноутбуков

Команды:

```bash
make dist-public
make dist-auth
```

Лестница нагрузки:

- 100 VUs total;
- 300 VUs total;
- 500 VUs total;
- 1000 VUs total только после стабильных меньших прогонов.

Позитивный результат:

- отчеты со всех машин суммарно показывают стабильность;
- нет машины, которая стала локальным бутылочным горлышком;
- серверные метрики подтверждают входящую нагрузку.

### Этап 5. State-changing сценарии

Команда:

```bash
make flight-once
```

Позитивный результат:

- один старт дает один `flightId`;
- одно завершение дает одну награду;
- профиль после полета корректен;
- нет дублей, отрицательных балансов, зависших полетов.

## Критерии успешности

| Слой | Успех |
| --- | --- |
| Public API | `http_req_failed < 1%`, checks > 99%, p95 < 800 ms, p99 < 1500 ms |
| Auth game open | `http_req_failed < 1%`, checks > 99%, p95 < 1000 ms, p99 < 2000 ms |
| Flight critical | `http_req_failed < 2%`, checks > 98%, p95 < 1500 ms, p99 < 3000 ms, бизнес-состояние корректно |
| Browser smoke | mobile viewport открывает игру, canvas появляется, старт полета работает |
| Distributed run | результаты с разных ноутбуков согласованы и не упираются в одну локальную машину |

## Стоп-условия

Останавливаем прогон, если:

- HTTP errors выше 1-2%;
- появились 401/403 на валидных токенах;
- появились 429, если rate limit не был целью теста;
- 5xx растут несколько минут подряд;
- p95/p99 резко растут без восстановления;
- игровой профиль повреждается или становится неконсистентным;
- бизнес-владелец просит остановить production нагрузку.

## Данные и подготовка

- Отдельные тестовые аккаунты под Yandex ID.
- Для read-only желательно 1 session token на 1-5 VUs.
- Для state-changing лучше 1 аккаунт на 1 активный VU.
- Доступ к backend логам, CPU/RAM/DB метрикам и ошибкам 4xx/5xx.
- Согласованное окно запуска на production.
- Понимание игровых лимитов: дневные полеты, валюта, билеты, попытки карусели.

## Риски

- Production может получить реальную нагрузку и повлиять на пользователей.
- Один аккаунт под высокой конкуренцией дает ложные ошибки.
- State-changing тесты меняют прогресс и экономику аккаунта.
- Browser tests плохо масштабируются на ноутбуках и не заменяют API load.
- Без серверных метрик нельзя точно понять, где узкое место: API, база, внешняя авторизация, сеть или клиент.

## Минимальный ближайший прогон

1. `make ping`.
2. `make auth-status`.
3. `make public-10`.
4. `make public-50`.
5. `make auth-1`.
6. Если токен валиден и все стабильно: `make auth-5`.
7. Только после этого переходить к `auth-50`, `auth-100` и distributed run.
